四、根据已完成的字段保真审计，生成标准恢复 manifest

审计资料目录：
D:\finance-history-migration-2026-09-05\

优先使用：
- reports\field-fidelity-audit.md
- reports\field-fidelity-audit-evidence.json
- 迁移时的 normalized ledger / imported ID 清单
- Notion 页面镜像支付方式 Relation 证据

生成一个标准 JSON manifest，格式严格参考：
docs/finance-fidelity-recovery-manifest.example.json

manifest 要求：

每个待恢复 transaction 必须包含：
- transaction_id：必须是现有 D1 historical transaction ID
- transaction_type
- category_name：来自 normalized historical ledger 的原始分类文本，不得由 AI 猜测
- expected_current_category：当前 D1 只读查询得到的分类名
- expected_current_account：当前 D1 只读查询得到的账户名
- payment_method：
  - 唯一可靠候选 => status=resolved + name
  - 多候选冲突 => status=ambiguous + candidates
  - 无可靠来源 => status=missing
- evidence：写明类别来源和支付方式来源，禁止放 Token/Secret/API Key

特别要求：
- “烟酒”等原始分类必须原样恢复，不再压缩为“其他支出”。
- 4 条支付方式冲突必须保持 ambiguous，不得自动拍脑袋选择。
- 没有可靠支付方式来源的记录保持未指定。
- 不推断不可恢复的二级分类、商家、备注或 Relation 对象语义。

五、生成离线恢复 SQL（只生成，不执行生产）

运行：

npm run finance:recovery:plan -- --manifest <manifest.json> --out-dir <output-dir>

必须得到：
- apply.sql
- rollback.sql
- summary.json

检查：
- apply.sql 只允许新增缺失 taxonomy（categories/accounts）、写 recovery journal、更新 category_id/account_id；
- 不允许改 amount_fen、currency、type、occurred_at、description、merchant、raw_text、source、source_id；
- 每条 UPDATE 都必须先通过 transaction id + expected current category + expected current account guard 写入 recovery journal；
- ambiguous/missing payment 不得被自动更新账户；
- rollback.sql 能按 run_id 恢复每条记录原来的 category_id/account_id。
